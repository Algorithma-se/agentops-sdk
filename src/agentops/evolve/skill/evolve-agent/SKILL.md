# Evolve Agent

Improve the requested agent autonomously with one tool, run from the client repository root (where `core/` is vendored):

- `agentops evolve …` (AgentOps Python SDK): `find`, `export`, `prompt pull`, `replay`, `assess`, `show`, `render`, `ask`, `publish`, `revert`. Pass `--env-file .env.evolve` to every command that talks to AOS Control (`find`, `export`, `prompt pull`, `ask`, `publish`, `revert`): it reads only `AGENTOPS_HOST`, `AGENTOPS_PUBLIC_KEY` and `AGENTOPS_SECRET_KEY` from that file and never prints them. Never source an env file into the shell. If `agentops` is not available in the client repo's environment, ask the user to add the SDK version that has `agentops evolve`.
- `agentops evolve replay … --env-file .env.evolve` runs the agent through core's `app.evolve_agent` module, so run it in the client repo's environment (`uv run agentops evolve replay …`). It loads the whole env file you pass (never `.env`) and refuses to run unless that file sets `LANGFUSE_SAMPLE_RATE=0`.

Inspect results through the CLI: `agentops evolve show <replay.json>` (compact text; `--full` for untruncated replies), the JSON of `find`, and the HTML; use a browser only if asked. Reuse frozen evidence and keep checks focused.

Reviewers write feedback in AOS Control: **"Agent feedback" page → Review tab**, or **session → "Agent feedback" tab**, per agent reply (scope _reply_) or for the whole conversation (scope _conversation_). Every edit is a new revision. Published replays ("Evolve replays") and your assessments appear next to the feedback on the "Review" tab; with "Show developer details" on, the list's replay picker shows one replay's conversations.

`core/` is read-only in client repositories: never edit, patch or commit anything under it. Change behaviour in the client's `config/` (agents.yaml, prompts, schemas), its hooks and tools, and — for agents with an AOS prompt — through a candidate prompt (see "AOS prompts").

## Replay environment (`.env.evolve`)

A replay runs the real agent: every hook (including `after_session`) and every tool runs as in production, with whatever credentials the env file holds. Only the conversation store is replaced, so nothing is written to Postgres.

- `.env.evolve` must hold only **read-only or sandbox** credentials (sandbox LLM key, read-only or test-tenant tool and data credentials, an AgentOps key for prompt reads). **Never use production write credentials**, and never point it at, or copy it from, the production `.env`.
- It must set `LANGFUSE_SAMPLE_RATE=0` and the `AGENTOPS_*` keys. The replay records each turn's trace events into the artifact instead of sending them; without the keys nothing is recorded and the run fails. Only `publish --apply` turns them into traces in AOS Control.
- Keep PII masking on: never clear `pii_categories_llm` or remove the masking provider's credentials to make a replay run. The replay sends the model the same LLM-masked buffer as the original trace's generations; the masking call (Azure Text Analytics or GCP DLP) is an expected external read. (`pii_categories_trace` is core's Postgres storage masking; a replay writes nothing to Postgres, so it does not apply, but leave it as configured.) If masking fails for lack of credentials, stop and ask the user for sandbox masking credentials.
- **Setup**: if `.env.evolve` does not exist, copy `env.evolve.template` (next to this SKILL.md) to `.env.evolve` in the repository root, make sure `.env.evolve` is git-ignored (add it to `.gitignore` if not), fill in only non-secret settings you can read from the repository (`PROJECT_ROOT`, `LLM_PROVIDER`, `MODEL_DEPLOYMENT_NAME`, the MCP server names in `agents.yaml`), then stop and ask the user to fill in the read-only or sandbox credentials. Never copy values from `.env`.
- **Verify before every replay**: read `.env.evolve`, confirm `LANGFUSE_SAMPLE_RATE=0`, and confirm every credential is read-only or sandbox. If you cannot tell whether a credential can write, stop and ask the user; never fill in credentials yourself.
- **Side effects (check before the first replay).** A replay sets `request_meta["_evolve_agent_replay"]`. List every hook in `agents.yaml` and every tool the agents use, and find the ones that act outside the conversation (send a message, create or change a ticket, write to a customer system). Each hook must be held back in a replay: mark it `@side_effects` (or `@side_effects(replay=stand_in)` when the agent needs a realistic result; from `app.agents.session.hooks`). A replay runs only tools annotated with MCP's `readOnlyHint: true`; every other tool, also one without annotations, is held back and the model gets "Not run in an Evolve Agent replay". Delegation (`invoke_agent`, `invoke_agents_concurrent`, `handover_to_agent`) runs in-process and is not held back; the other agent's tools get the same check. So annotate each tool that only reads with `readOnlyHint: true` (`annotations=READ_ONLY` from `app.tools.mcp_tools.annotations` in this repository's MCP server), and never one that sends or writes; a held-back tool can also return a stand-in itself when its `_meta` has `_evolve_agent_replay`. Add a missing mark as part of the task commit when the code is in this repository. If the code is elsewhere, or you are not sure whether something has side effects, stop and ask the user before replaying.
- Every process of the replay reads only `.env.evolve`, also core's tool server and `--local-mcp` servers; `.env` is never read. So the settings of a tool server started for the replay (its read-only or sandbox credentials) belong in `.env.evolve` too.
- **Tools from this repository.** A plain tool name in an agent's `tools` (e.g. `- get_order_status`) runs in core's own tool server, which every replay starts from the current checkout: it needs nothing more. A `<server>:` block (e.g. `- shop: [get_order_status]`) calls the MCP server at `MCP_URL_<SERVER>`. When that server's code is in this repository (e.g. an `mcp_server` module next to `config/`), always replay with `--local-mcp <NAME>="<command>"` (repeatable; `<NAME>` as in `agents.yaml` and `MCP_URL_<NAME>`). Take the command from the repository's own docs on running its MCP server locally (its README or an MCP server doc); if they do not say, stop and ask the user. The command must start the server in its MCP-server mode, serve HTTP on `127.0.0.1` at port `{port}` (also in `$PORT`) with the endpoint `/mcp`, and accept the key the agent sends (`$MCP_API_KEY_<NAME>`), e.g. `--local-mcp <name>="MCP_PORT={port} MCP_API_KEY=$MCP_API_KEY_<NAME> <the repository's start command>"`. The replay starts it from the current checkout, points `MCP_URL_<NAME>` at it, and stops it afterwards, so a changed tool is what the replay tests; it records `provenance.tool_servers.<name> = "local"`. Never replay against an already running or deployed server of this repository after changing a tool: it runs other code than the commit the replay records. The server's log is `mcp-<name>.log` next to `replay.json`. Servers from other repositories keep their `MCP_URL_<NAME>`.

## Agents in this repository

One AOS project can hold traces of many agents, built in different repositories. Work only on the agents this repository defines:

- List the agent names in this repo's `config/agents.yaml` (the keys under `agents:`) before selecting anything. `find` and `export` use them by default; `--trace-name <agent>` (repeatable) picks fewer. A name also matches its variants (`support/<variant>`).
- Feedback is filed under the agent that **started** the turn (its trace name). After a handover the replay starts at that agent again and hands over from the frozen history.
- A turn is replayed with the images the user sent (`source.attachments`; replay downloads them from AOS Control) and with the `request_meta` and `user_context` recorded on the original trace (`source.request_meta`, `source.user_context`); a trace named `support/v2` also gets `"agent_variant": "v2"`. Core records only the keys an agent lists in `agents.yaml` under `evolve_agent: {trace_context: [...]}` (for example `brand`, `market`); they are stored unmasked, so never list a key that can hold personal data. A turn recorded without them has neither: say so when its brand or user context matters, and suggest the keys to list.
- The replay checks every entry's `agent_name` against the local agents config before running anything and stops with the list of unknown agents. If it does, the export picked up another repository's agents: export again with the right agents; never add agents to `agents.yaml` to get past it.

## Workflow

1. **Select evidence.** `agentops evolve find --env-file .env.evolve --feedback unresolved [--session <id> …]` lists this repo's turns with feedback items that still need work: `state` `open` or `partial`, or `fixed`/`closed` by a commit `HEAD` does not contain. Items that wait for an answer (`needs_input`) or that a reviewer dismissed are never listed, and replies are not items of their own. Read each note, its `thread[]` (oldest first: reviewers' `reply` entries, your `question` entries with `status` and `answered_by`, and `dismissed`), the reviewed turn, the earlier conversation and previous assessments (`assessments[]`). A reply is context for its item, not separate work; a reply with `answers` set is the answer to that question. A note with `replay_run_id` is about that Evolve replay's reply, not the original: read its `replay` (`git_commit`, `replay_name`, `reply`), because the frozen turn shows the original reply. If `HEAD` contains that commit, build on that change instead of starting over from the original; if not, say so. Items with a `source` other than `reviewer` came from a scanner (e.g. `frustration_tool`; raw data in `payload`). Keep the reviewer's wording when summarizing. Explain any exclusion, and never drop a failing target. `--feedback <state>[,<state>…]` lists stored states instead (e.g. `needs_input`); `--feedback-id` and `--session` are repeatable. Also pick a regression set (see "Regression set"). **Then post the first progress table (every row _pending_, see "Progress table") before you freeze, change or replay anything.**
2. **Freeze, once per task.** `agentops evolve export --env-file .env.evolve --feedback unresolved [--session <id> …] --output local/evolve/<name>-target.json` freezes, in one step, every turn that the same `find` selection returns: the history before it and the user message (from the first model call), the original reply, the original system prompt (`source.system_prompt`) and linked AOS prompt version (`source.prompt`), and every current feedback revision on that turn. Freeze the regression set into a **separate** file with explicit ids: `agentops evolve export --env-file .env.evolve --trace-id <trace> [--trace-id <trace> …] --output local/evolve/<name>-regression.json`. Export once per task and reuse the frozen files across iterations; export again only when new feedback arrives. An export never overwrites a file and writes nothing to AOS Control.
3. **Change, then commit before replay.** Make focused changes and run focused checks for consequential behaviour. Canned-answer tests are no substitute for replays. Work on the **current branch**; use another branch or worktree only if asked or needed to protect unrelated work. Keep **one task commit**: create it after the first change, then amend and reword it to cover everything done so far. Use the repo's title style and a body explaining the problem, the changes, validation and limitations. Stage only task files, keep unrelated changes, and never amend someone else's commit. Commit (or amend) before every replay without pausing for approval: a replay of a dirty tree cannot be published.
4. **Replay.** After verifying `.env.evolve` (see above), `uv run agentops evolve replay <frozen.json> --env-file .env.evolve --name <short-name> [--prompt NAME=local/evolve/prompts/NAME.txt …] [--local-mcp NAME="<command>" …]` (always `--local-mcp` for a tool server served from this repository, see "Replay environment") runs each turn through the real agent with its frozen history and the current code, prompts and model. No replay sends traces: each run's trace events are recorded in `run.events`. **Never read `run.events` or open `replay.json` directly** (the events are large and only for publishing); read runs with `agentops evolve show <replay.json>`: provenance, status, prompt, tools in call order, original and replay reply, repeats, feedback and assessments. It writes `local/evolve/<date>_<NN>-<name>/replay.json` (or `--output <new file>`) and the adjacent `replay.html` comparison, with each run's final system prompt (`run.system_prompt`) and, for AOS-prompt agents, the prompt name and version (`run.prompt`). The frozen file is never changed. `agentops evolve render <replay.json>` writes the HTML again. Tools run live with current data, so results can differ from the original for reasons other than your change; say so in the assessment when it matters. Replay target and regression files separately. When a fix depends on model behaviour rather than code (wording, a judgement call, a tool the model may or may not choose), replay with `--repeat 3`: the extra runs land in `run.repeats` (no events, never published), `show` counts them, and you report the result as e.g. "3 of 3" or "2 of 3".
5. **Assess.** For every relevant frozen feedback revision run `agentops evolve assess <replay.json> --run-id <run_id> --feedback-id <id> --status <fixed|verified|partial|unresolved|regressed|blocked|superseded|wontfix> --explanation "…" --evidence "<what the replay actually did>" --changes "<what this commit changed>" --author "<you>"`. Instead of `--run-id` you can pick the entry with `--trace-id <source trace id>` or `--session <id>` (an error if several entries match). The CLI prefixes `changes` with the replay's SHA and regenerates the HTML. Be truthful: say when the behaviour already existed or is still unresolved. Compare decisions, tool calls and wording against the original, the reviewer's note and earlier iterations. Compare the prompts too: the HTML shows the original and replay final prompt text side by side with their name/version badges, and whether the prompt changed (by `(name, version)` when both sides have one, else by text). An unexpected prompt difference (another version than you meant, a changed context value) is a finding to report, not noise. If resolving a feedback needs a fact only the reviewers have (sources disagree, a policy is unclear, the note is ambiguous), do not guess and do not mark it `blocked` silently: ask one specific question (see "Needs input"). Use `blocked` only when nobody can answer it with a reply: the agent or the replay lacks something (a tool, a data source, an input the replay cannot give). Say in `--explanation` what is missing and what would unblock it; reviewers see that text under the replay and a "Blocked" badge on the conversation.
6. **Iterate and verify.** Repeat steps 3–5 while actionable feedback, material regressions or evidence-backed improvements remain. Stop at a clearly improved baseline, or name the missing policy or evidence that blocks progress. Before finishing, verify that the final target and regression artifacts have `provenance.git_commit` equal to `git rev-parse HEAD`, that every final assessment names that SHA, and that the final target artifact contains only target turns. An earlier artifact proves only its own SHA, so any later commit change needs a new replay and new assessments.

A turn replay proves the behaviour for that turn with that history. It does not prove a whole conversation outcome. Later user messages are never replayed automatically, because their meaning may depend on the old reply.

### Regression set

The regression set guards against the change making other turns worse. Pick it in step 1, before any change, with `agentops evolve find --env-file .env.evolve …` (original turns only, JSON with `trace_id`, `session_id`, `user_message`, `reply`, `tools`, `votes`, `feedback_states`, `similarity`, `feedback`; default the last 7 days, `--since 30d` for more):

1. For each target turn: `find --like <target trace_id> --limit 5` (same agent, other sessions, same tools in the same order by default). Take the top 1–3 that are not target turns. Add `--any-tools` when the change is about wording rather than tool use, or when the same-tools search finds too little.
2. Add 2–3 turns reviewers approved: `find --vote up`.
3. Add the turns of earlier fixes as guards (fixes must not regress): `find --feedback fixed`.
4. For breadth, add 1–2 recent turns of the same agent that use other tools: `find --trace-name <agent> --feedback none`.

Aim for 5–15 turns. Never include target turns or turns of the target sessions: save the target selection first (`find --env-file .env.evolve --feedback unresolved … > local/evolve/<name>-find.json`), then pass `--exclude local/evolve/<name>-find.json` to every `find` above and to the regression `export`. It skips every session in that file (a frozen file works too). `find` prints the count (`N turn(s), M feedback item(s)`) to stderr; use it in the progress table. Explain the choice in one or two lines with the first progress table, then freeze them with `export --trace-id … --output local/evolve/<name>-regression.json`.

## AOS prompts

Agents with an AOS prompt take their instructions from AOS Control's prompt management, not from the repo. Change them through a local candidate; nothing reaches AOS Control before publishing:

1. `agentops evolve prompt pull NAME --env-file .env.evolve [--label production]` writes `local/evolve/prompts/NAME.txt` and `NAME.json` (`base_version` = the version the label points to now).
2. Edit `NAME.txt`. Keep it a valid Jinja template for the same context.
3. Replay with `--prompt NAME=local/evolve/prompts/NAME.txt` (repeatable). The replay serves the local text instead of fetching the prompt and records `run.prompt` with `version: null`, `candidate: true`, the base version and the text's sha256; code changes in the same iteration are committed as usual (the candidate file under `local/evolve/` does not make the tree dirty). Nothing is pushed while iterating.
4. Accept the candidate only with replay evidence, like any change, and keep the candidate file unchanged after the final replay.
5. `agentops evolve publish <replay.json> --env-file .env.evolve --apply` (only when the user asks) refuses if the file changed since the replay or the label moved away from the base version, then creates the new prompt version **without labels** and publishes the replay with it.
6. A person promotes the new version (moves `production` or another serving label) in AOS Control; a release gate may apply. Never move or set a label yourself, and never create prompt versions any other way.

## Needs input

`agentops evolve ask --env-file .env.evolve --feedback-id <id> --question "…" --author "<developer>" [--revision <the revision you read>]` posts a question about the item to AOS Control in the developer's name: `<developer>` is the output of `git config user.name` in this repository, so reviewers know whom they answer (naming a revision that is no longer current is a 409: read the item again). It shows in that feedback's thread and in the Agent feedback page's **Questions for you** tab, where anyone can answer with a reply in the thread (or the author by editing the note).

- Ask one concrete question per feedback, with the options you see (e.g. "Two sources give different Saturday hours: 10–16 (website) and 10–18 (store config). Which is right?"). Never ask for credentials or personal data.
- Until someone answers, the item is `needs_input` and `--feedback unresolved` skips it; `find --feedback needs_input` lists what is waiting. Asking again about the same item returns the open question.
- Once answered, the item is open again. In its `thread[]` the question has `status: "answered"` and `answered_by`: the `revision` of the reply that answered it, or a newer revision of the note itself (see `history[]`; export again to freeze it). Read the answer, then continue the loop.
- A question you no longer need: `agentops evolve ask --env-file .env.evolve --withdraw <question id>`.
- An assessment you save after asking does not close the question: it stays in **Questions for you** until someone answers it or you withdraw it. The item then takes the assessment's state (e.g. `partial`), so `--feedback unresolved` lists it again and `find --feedback needs_input` does not; its `thread[]` still shows the question as `open`.
- In the progress table, mark asked items _needs input_ with the question.

## Progress table

Post a Markdown table in chat after evidence selection and after every iteration's assessments are saved, before starting the next iteration. Columns: **Agent** (the trace name, e.g. `support` or `support/v2`), **Session / turn**, **Feedback / work**, **Status** (_pending_, an assessment status, or _needs input_), **Observed result / remaining work**.

- The first table is required and comes at the end of step 1, before any export, change or replay. It lists every selected feedback item and describes planned work; mark every row _pending_.
- Each later table is built from that iteration's target `replay.json`: name the iteration and its SHA and link the artifact. Include every target turn, including partial, blocked, unresolved, regressed and failed ones. Summarize multiple revisions in one row without hiding an open issue.
- Keep the feedback summary faithful to the reviewer's text. Keep observed results separate from proposed next changes.
- Report regression results separately from this table.

## Publishing

Preview the verified final target artifact with `agentops evolve publish <replay.json> --env-file .env.evolve` (no `--apply`: nothing is sent). It prints every entry's prompt comparison, feedback and assessments and the prompt versions it would create, then checks locally that the artifact and the working tree are clean, that the replay commit is `HEAD`, that every assessment names a frozen revision and the SHA, that every run completed with recorded trace events, that the artifact belongs to the API key's project, and that each candidate prompt file is unchanged since the replay and its label still points to the base version. With `--apply` it then creates one unlabelled prompt version per candidate (commit message `Evolve Agent: <replay name>`) and publishes the replay with those versions; AOS Control repeats the checks and stores the publication. **Never run `publish --apply` (or `revert --apply`) unless the user explicitly asks.** `agentops evolve revert <replay.json> --env-file .env.evolve --apply` withdraws a publication. Publishing adds the replay and assessments to AOS Control, creates a new unlabelled version per candidate prompt, and leaves the original sessions and the serving prompt labels unchanged. Local replays and commits send nothing to end users.

Report the final code SHA, the final target artifact path, the separate regression artifact path, any candidate prompts (name, base version, file), outcomes, checks run and limitations. End the final response with the publish command for the user to run, with the real path filled in. Showing it does not authorize running it:

`agentops evolve publish <final-target-artifact> --env-file .env.evolve --apply`
